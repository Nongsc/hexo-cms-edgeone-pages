# 架构与交付说明

> **注意**：本文档记录了开发过程中各轮迭代的演进，部分早期描述（如
> "Edge Functions"、`dist-edge`、`workflow_dispatch` 部署、部署日志等）
> 已在后续迭代中调整。**以当前为准的架构总览、功能清单与部署方式，请以
> [README.md](../README.md) 与 [部署指南.md](./部署指南.md) 为准。**

## 一、设计目标

复刻 Hexo-Pro 的后台管理能力，并将其重构为一个**纯 Web 应用**：

1. **部署形态**：部署在腾讯云 EdgeOne Pages，不依赖桌面端与本地 Hexo 运行时。
2. **内容管理**：通过 GitHub API 读写博客仓库，不再操作本地文件。
3. **数据源**：CMS 自身使用 SQLite 持久化（站点配置、文章元数据、待办、部署日志）。
4. **图床**：图片资源统一存放腾讯云 COS，CMS 不落盘。
5. **UI**：基于 pure-admin 规范重建。
6. **编辑器**：monaco-editor-vue3。
7. **架构**：严格 MVC 分层。

## 二、MVC 分层与职责边界

```
┌──────────────────────────────────────────────────────────────┐
│  Browser                                                     │
│    views/            ← 用户可见的 View（Vue 组件）              │
│    router/           ← 前端路由与登录守卫                       │
│    store/            ← Pinia 状态                              │
│    api/              ← HTTP 客户端（统一响应拦截）                │
└───────────────────────┬──────────────────────────────────────┘
                        │  /api/*
                        ▼
┌──────────────────────────────────────────────────────────────┐
│  EdgeOne Edge Functions (Hono)                               │
│                                                              │
│  router.ts            ← View：REST 端点、CORS、鉴权中间件        │
│       │                                                      │
│  controllers/         ← Controller：协议适配                    │
│       │                   · 参数校验                            │
│       │                   · 调用 Service                        │
│       │                   · 统一响应结构 {code,message,data}      │
│       │                   · 异常 → HTTP 状态映射                  │
│       ▼                                                      │
│  services/            ← Service：业务规则与编排                  │
│       │                   · 事务边界                            │
│       │                   · 双写策略（SQLite + GitHub）           │
│       │                   · 外部服务调用                          │
│       ├──────────────► repositories/  ← Model：SQL 访问          │
│       │                                                      │
│       ├──────────────► GitHubClient   ← GitHub REST API        │
│       └──────────────► CosClient      ← COS XML API            │
└──────────────────────────────────────────────────────────────┘
```

### 各层约束

| 层 | 允许依赖 | 禁止 |
| --- | --- | --- |
| Model（db / repositories / types） | `node:sqlite`、纯类型 | 任何外部 API、HTTP 概念 |
| Service | Model、GitHubClient、CosClient | Hono / Request / Response |
| Controller | Service | 直接访问 Repository（绕开业务规则） |
| View（router.ts） | Controller | 业务规则 |

这一约束由测试与类型检查共同保证：`packages/core` 不依赖 `hono`，
`apps/api` 不直接 import `repositories` 中的查询细节。

## 三、关键设计决策

### 3.1 双写策略：SQLite 为源，GitHub 为输出

```
用户保存文章
    │
    ├──► SQLite（CMS 数据源）──► 列表 / 搜索 / 统计 / 仪表盘
    │
    └──► GitHub API（Hexo 输入）──► hexo generate
```

- **读全部走 SQLite**：保证响应速度，且不消耗 GitHub API 配额。
- **写同时落两处**：保证 Hexo 能构建出最新内容。
- **GitHub 失败不阻塞 UI**：保存仍算成功，但在界面明确提示同步失败原因。

### 3.2 使用 `node:sqlite` 而非 better-sqlite3

Node.js 22.5+ 与 Edge Functions 的 Node runtime 均内置 `node:sqlite`：

- 无需原生编译 → 安装与 CI 更稳定；
- 无二进制体积 → Edge bundle 仅 367 KB；
- API 为同步式，与 Repository 层的调用模型天然匹配。

### 3.3 部署触发而非本地构建

CMS 解耦后不包含 Hexo 运行时，因此：

```
CMS「部署」按钮
    │
    ▼
GitHub API: POST /actions/workflows/{workflow}/dispatches
    │
    ▼
博客仓库的 GitHub Actions
    │
    ├──► hexo generate
    └──► 发布到 EdgeOne Pages / GitHub Pages / Cloudflare Pages
```

CMS 只负责记录与展示部署日志，构建与发布完全由 CI 完成。
工作流模板见 `deploy/hexo-blog-deploy.yml`。

### 3.4 COS 直连签名

图床上传走 COS XML API 的 `PutObject`，使用 TC3-HMAC-SHA256 签名：

- 不需要引入 `cos-nodejs-sdk-v5`（体积大且部分 API 需 Node 兼容层）；
- 上传 / 列表 / 删除 / 建目录四个操作足够覆盖图床需求；
- 元数据同时写入 SQLite `assets` 表，便于分页与去重。

### 3.5 前端路由与鉴权

- 登录态使用内存 Map 会话 + Bearer Token（与无服务器形态匹配）；
- 前端路由守卫保证未登录跳转 `/login`；
- Axios 响应拦截器统一处理 `code === 401`（登出并跳转登录页）。

## 四、数据模型

```
settings          站点配置（分组：general / github / cos / ai / deploy）
                  · 敏感字段标记 is_secret，接口返回时打码

documents         文章与页面（kind: post | page）
                  · status: published | draft
                  · deleted_at 非空表示在回收站
                  · tags / categories 以 JSON 数组存储
                  · repo_path 对应仓库中的 Markdown 路径

todos             待办事项

deploy_logs       部署记录（channel / status / message）

assets            COS 图片元数据（cos_key 唯一）

users             管理员账号（username + password_hash）

schema_migrations 迁移版本记录
```

索引：`documents(kind, status, deleted_at)`、`assets(folder)`。
外键：开启 `PRAGMA foreign_keys = ON`。
日志模式：WAL。

## 七、联调中修复的关键缺陷

本次用真实 GitHub 仓库与 COS 存储桶联调，修复了以下问题：

1. **数据库路径依赖启动目录**：`getDatabase()` 曾用 `resolve(process.cwd(), ...)`，
   从 `apps/api` 启动时会落到错误的嵌套路径，导致「换目录启动就丢配置」。
   现改为相对项目根目录解析（`resolveDatabasePath`），与工作目录无关。

2. **COS 签名失效（SignatureDoesNotMatch）**：初版 TC3 签名对 COS XML API 不兼容，
   改为 AWS SigV4（COS 的 S3 兼容端点原生支持）。修复了两处细节：
   - 查询参数必须按字母序排列（`max-keys` 在 `prefix` 前）；
   - `prefix` 值中的 `/` 必须编码为 `%2F`。
   自定义域名仅用于生成图片公网 URL，API 调用走默认端点签名。

3. **Repository 读行字段映射错误**：`SELECT *` 返回的列是下划线风格
   （`repo_path`、`front_matter`、`published_at`），而 `DocumentRecord` 是
   camelCase，导致 `row.repoPath` 为 `undefined`，进而 GitHub 双写时
   `encodePath(undefined)` 抛 500。已用独立的 `DocumentTableRow` 类型对齐。

4. **`/auth/me` 未挂鉴权中间件**：原路由将 `/auth/me` 放在免登录段，导致
   `c.get("session")` 恒为 undefined 返回 401。已将其与
   `/auth/change-password` 一并移到鉴权中间件之后。

## 八、已知限制与后续工作

1. **会话持久化**：当前会话在进程内存中，Edge Functions 冷启动会丢失。
   需要长期会话时可把 `AuthService.sessions` 改为 SQLite 存储。
2. **SQLite 持久化**：Edge Functions 的文件系统持久性取决于平台配置。
   关键数据建议定期备份到 COS，或将 Repository 切换到平台托管数据库。
3. **AI 创作助手**：配置项已预留，能力尚未实现（见功能梳理文档 T2）。
4. **多用户与权限**：当前为单管理员模型。
5. **COS 安全**：长期密钥直接配置在 CMS 内；生产建议改用 STS 临时密钥下发。
6. **前端体积**：Monaco 与 Element Plus 分包后仍较大（合计约 4.8 MB），
   已按 vendor 拆包利用浏览器缓存，进一步优化可考虑 Monaco 按需加载语言。

## 九、第二轮联调修复记录（按用户反馈）

1. **文章状态以 GitHub 为准**：`syncFromGitHub` 现在同步完成后做「对账」——
   本地标记为「已发布」但 GitHub 仓库 `source/_posts` / `source/pages` 中
   已不存在的文档，自动降级为草稿（返回 `downgraded` 计数），前端同步提示
   明确告知。

2. **页面编辑器「返回」按钮回到错误列表**：编辑器的 `kind` 原依赖
   `route.query.kind`，但列表页 `goEdit` 不带 query，导致页面被误判为文章。
   改为从路由路径判断（`/content/page-editor` → page），保存后 `router.replace`
   也按 kind 回到对应编辑器路径。

3. **发布文章路径错误（source/pages/source/_posts/...）**：`buildPath` 曾把
   含 `/` 的 `sourcePath`（实为完整路径）误当「页面自定义子目录」再拼一层
   `source/pages/`。重写路径计算：`buildPath(kind, slug, status, sourcePath)`
   明确区分文章/页面的标准目录，页面子目录用 `pageSubDir` 规范化，
   更新时用 `extractSubDir` 从旧路径提取子目录。已清理仓库中由此产生的
   历史错误路径文件。

4. **YAML 配置改为「快照草稿 + 发布」工作流**：
   - 左侧配置文件列表（`_config.yml` + `_config.<theme>.yml`），右侧编辑；
   - 「保存草稿」写入 SQLite 的 `config_snapshots` 表（不推送）；
   - 「发布」推送到 GitHub 后清除草稿；「丢弃草稿」恢复 GitHub 版本；
   - 新增 `ConfigService`、`ConfigSnapshotRepository`（迁移 v2）与
     `/api/config` 系列接口。

5. **主题管理改为 GitHub Actions 安装**：
   - 提供 git clone 地址、目录名、分支、包管理器（npm/pnpm）、
     依赖包、Hexo 插件输入项；
   - 通过 `workflow_dispatch` 触发博客仓库的 `install-theme.yml` 工作流；
   - 工作流模板（`deploy/install-theme.yml`）支持 clone、主题依赖安装、
     额外依赖包与插件安装、提交推送。

## 十、第三轮联调修复记录（按用户反馈）

1. **页面列表为空（Hexo 页面结构错误）**：此前把 Hexo 页面误当
   `source/pages/<name>.md`，而 Hexo 标准页面结构是 `source/<name>/index.md`
   （如 `source/about/index.md`）。全面修正：
   - `DOCUMENT_PATHS.page` 改为 `source`（页面）/ `source/_drafts`（页面草稿）；
   - `buildPath` 页面生成 `source/<slug>/index.md`，草稿生成
     `source/_drafts/<slug>/index.md`；
   - `syncFromGitHub` 识别 `source/*/index.md`（排除 `_posts`、`_drafts`、
     `images` 等保留目录）；
   - 同步后页面列表正确显示 `about`、`categories`、`links`、`tags` 四个页面。

2. **YAML 配置文件应从 GitHub 仓库动态获取**：`ConfigService.listFiles()`
   改为从仓库根目录读取所有 `_config*.yml`（不再硬编码），与仓库实际内容同步。
   用户仓库中的 `_config.yml`、`_config.butterfly.yml`、`_config.landscape.yml`、
   `_config.yun.yml` 全部正确列出，并标注「当前使用」的主题配置。

3. **主题安装 git clone 与命令行二选一**：`ThemeInstallInput` 新增
   `installMethod: "git" | "npm"`，前端弹窗用单选按钮切换两种方式：
   - git clone：填写 Git 地址 + 目录名 + 分支；
   - 命令行：填写 npm/pnpm 包名（如 `hexo-theme-landscape`）。
   后端按方式校验必填字段，`install-theme.yml` 工作流分别执行
   `git clone` 或 `npm/pnpm install`，两者互斥。

## 十一、第四轮功能增强（按用户需求）

1. **主题管理展示已安装插件（避免重复安装）**：
   `ThemeService.listPlugins()` 从博客仓库 `package.json` 的
   dependencies / devDependencies 中筛选 `hexo-` 开头的包，
   前端主题页以标签形式展示，安装主题时参考此列表避免重复安装。
   新增 `GET /api/themes/plugins` 接口。

2. **文章编辑器添加简介与 Front Matter 编辑器**：
   - 顶部元数据区新增「简介」多行输入（对应 frontMatter 的 `description`）；
   - 新增可折叠的「Front Matter（自定义字段）」Monaco YAML 编辑器，
     展示除 title / tags / categories / cover / sticky / description /
     date / updated / published 等保留字段之外的自定义字段；
   - 保存时用 `js-yaml` 把 YAML 文本解析为对象，作为 `frontMatter`
     传给后端合并，非法 YAML 静默忽略不阻断保存。

3. **页面编辑器同样支持 Front Matter 编辑器**：编辑器组件是文章/页面
   共用的（按路由区分 kind），因此页面编辑器天然获得简介与
   Front Matter 编辑器能力，与文章一致。

## 十二、第五轮功能增强（按用户需求）

1. **主题管理支持安装/卸载/停用**：
   - 安装：git clone 或 npm/pnpm 二选一（已有）；
   - 卸载：`ThemeService.uninstall()` 触发 `manage-theme.yml` 工作流，
     git 来源删除 `themes/<name>`，npm 来源 `npm uninstall hexo-theme-<name>`
     （并兜底从 package.json 移除）；不能卸载当前启用的主题；
   - 停用：`disable()` 将 site.theme 切回默认 landscape；
   - 新增 `POST /api/themes/uninstall`、`POST /api/themes/disable`。

2. **命令行安装的主题显示**：`ThemeService.list()` 改为合并两处来源——
   themes 目录（git）与 package.json 中 `hexo-theme-` 开头的包（npm），
   包名去掉 `hexo-theme-` 前缀得到主题名（如 `hexo-theme-landscape` → `landscape`），
   返回 `{ name, source, active }`。`listPlugins()` 相应排除 `hexo-theme-`
   前缀（那是主题不是插件）。

3. **YAML 配置支持新建/删除**：
   - 全局 `_config.yml` / `_config.yaml` 不允许删除（后端校验）；
   - 主题配置 `_config.<theme>.yml` 支持「新建」（先存草稿，发布后写入
     仓库）与「删除」（直接 `deleteFile`）；
   - `listFiles()` 合并 GitHub 已有文件与本地草稿（新建未发布的配置也显示）；
   - 新增 `POST /api/config`（新建）、`DELETE /api/config/:path`（删除）。

## 十三、第六轮功能增强（按用户需求）

1. **启用的主题以 `_config.yml` 的 `theme` 值为准**：
   - `ThemeService.readActiveTheme()` 从博客仓库 `_config.yml` 读取
     `theme` 字段（值可能是 `hexo-theme-xx` 或去掉前缀的 `xx`），
     并同步到 SQLite `site.theme` 缓存；
   - `enable()` / `disable()` 改为**写回 `_config.yml` 的 theme 行**
     （行替换，保留所有注释与格式），再推送到 GitHub；
   - 修正了此前「SQLite 显示 yun 但 _config.yml 实为 fluid」的不一致。

2. **插件装上即启用**：Hexo 插件（hexo-generator-* / hexo-renderer-* 等）
   安装在 package.json 中即被 Hexo 自动加载，无「启用/停用」开关。
   前端「已安装插件」卡片更名为「已启用插件」，并注明自动启用说明。

3. **部署调整为 EdgeOne Makers 自动部署**：
   - 用户博客通过 EdgeOne Makers 关联 GitHub 仓库，push 即自动构建，
     无需 CI 工作流；
   - `DeployService.trigger()` 由「触发 workflow_dispatch」改为
     「通过 GitHub API 创建空提交（createEmptyCommit）」，人为触发一次
     push 让 EdgeOne 重新构建（如主题/依赖变更后手动刷新）；
   - 保存内容本身就会推送，因此「保存即部署」；部署按钮退化为手动重触发；
   - 前端部署页移除「工作流文件」输入，改为说明 EdgeOne 自动部署机制。
